## 1. Phase Overview

### What This Phase Is
Phase 2 implements the complete authentication and user management layer for the Alex AI backend. This includes JWT (RS256) token issuance and validation, refresh token rotation with reuse detection, Google OAuth 2.0 with PKCE, an encrypted Vault for storing OAuth tokens, bcrypt password hashing, brute-force protection, user profile CRUD, and account soft-deletion. From this point forward, every API endpoint except `GET /health` requires a valid JWT in the Authorization header.

### Why It Is Important
Authentication is the security gate for every feature that follows. Phase 3 (AI Model Router) will issue AI API calls on behalf of authenticated users. Phase 4 (Task Management) stores user-scoped data protected by RLS policies that depend on the `user_id` extracted from the JWT. Phase 5 (Calendar) requires the Google OAuth tokens stored by this phase's Vault service. Without Phase 2, no user-scoped feature is possible.

## 2. What Was Built

- **TokenService** — RS256 JWT issuance, access token decode with Redis blocklist revocation, refresh token rotation with SHA-256 hashing, reuse detection, JWKS public key endpoint
- **AuthService** — User registration (email uniqueness), login (bcrypt verify + brute-force lockout), refresh token rotation, logout (full revocation), Google OAuth login flow
- **OAuthService** — Google OAuth 2.0 authorize URL builder with PKCE (S256), authorization code exchange via Google token endpoint, `id_token` verification via Google JWKS, encrypted token storage in Vault
- **VaultService** — Local stand-in for Supabase Vault using Fernet (AES) encryption, encrypts/decrypts JSON blobs in `.local_vault.json`
- **PasswordService** — bcrypt hashing (12 rounds) and verification
- **UserService** — Profile fetch, update, password change (with current-password verification), account soft-deletion with 30-day grace period
- **Auth middleware** — `get_current_user` FastAPI dependency extracts JWT, decodes, loads user; `require_admin` secondary dependency
- **Pydantic schemas** — RegisterRequest (with password strength validation: 12-128 chars, upper, lower, digit, special), LoginRequest, RefreshTokenRequest, GoogleExchangeRequest, OnboardingTokenExchangeRequest, ChangePasswordRequest, DeleteAccountRequest, UserResponse, UserSummary, UpdateUserProfileRequest
- **API routes** — `POST /v1/auth/register`, `POST /v1/auth/login`, `POST /v1/auth/refresh`, `POST /v1/auth/logout`, `GET /v1/auth/oauth/google/authorize`, `POST /v1/auth/oauth/google/exchange`, `POST /v1/auth/onboarding/token-exchange`, `GET /.well-known/jwks.json`, `GET /v1/users/me`, `PATCH /v1/users/me`, `PUT /v1/users/me/password`, `DELETE /v1/users/me`
- **Configuration** — JWT settings (issuer, audience, key pair, expiry), Supabase JWKS federation, Google OAuth credentials and scopes, Vault encryption key

## 3. File-by-File Explanation

### `apps/api/app/services/token_service.py`
**Purpose:** Central token lifecycle manager
**What it does:** Issues RS256 JWTs with standard claims (sub, email, name, role, iat, exp, iss, aud, jti). Stores refresh tokens as SHA-256 hashes in Redis with 30-day TTL. Rotates refresh tokens on each use and detects reuse by checking a `auth:refresh_used:{hash}` key — if present, the entire token family for that user is revoked. Maintains a Redis blocklist (`auth:revoked:{jti}`) for revoked access tokens. Also supports Supabase JWKS decoding as a fallback for federated auth.
**Key functions/classes:** `TokenService`, `TokenBundle` (dataclass), `TokenPayload` (dataclass), `issue_tokens()`, `rotate_refresh_token()`, `decode_access_token()`, `revoke_access_token()`, `get_jwks()`
**Generated by:** Codex

### `apps/api/app/services/auth_service.py`
**Purpose:** Authentication business logic
**What it does:** Orchestrates user registration with email uniqueness check (case-insensitive), login with bcrypt password verification and brute-force protection (5 failures → 30-min lockout), token refresh via rotation, logout with full revocation, and Google OAuth login (find-or-create user, store Google tokens in Vault).
**Key functions/classes:** `AuthService`, `AuthResult` (dataclass), `register_user()`, `login_user()`, `refresh_tokens()`, `logout_user()`, `login_with_google()`
**Generated by:** Codex

### `apps/api/app/services/oauth_service.py`
**Purpose:** Google OAuth 2.0 integration
**What it does:** Builds the Google authorization URL with PKCE (`code_challenge` + `S256`), exchanges the authorization code for Google tokens via `https://oauth2.googleapis.com/token`, verifies the `id_token` using Google's JWKS public keys, and stores the Google access/refresh tokens encrypted in the Vault.
**Key functions/classes:** `OAuthService`, `GoogleIdentity` (dataclass), `build_google_authorize_url()`, `exchange_google_code()`, `store_google_tokens()`
**Generated by:** Codex

### `apps/api/app/services/vault_service.py`

Provides `put_json()`, `get_json()`, and `delete()` operations. Generates OAuth storage keys via `oauth_key()`.
**Key functions/classes:** `VaultService`, `put_json()`, `get_json()`, `delete()`, `oauth_key()`
**Generated by:** Codex

### `apps/api/app/services/password_service.py`

## 4. Flow Explanation (Technical)

### Login Flow (Email + Password)

1. Client sends `POST /v1/auth/login` with `{email, password}` to `routes/auth.py:login_user()`.
2. Route creates an `AuthService` instance (injected with `TokenService`) and calls `auth_service.login_user()`.
3. `AuthService._enforce_lockout()` checks Redis for `auth:login_lock:{email}`. If locked, returns `429 ACCOUNT_LOCKED`.
4. `AuthService` queries the `users` table for a matching email (case-insensitive, `deleted_at IS NULL`).
5. `password_service.verify_password()` compares the submitted password against the stored bcrypt hash.
6. On failure: `AuthService._register_failed_login()` increments `auth:login_fail:{email}` in Redis. After 5 failures, sets `auth:login_lock:{email}` with 30-minute TTL.
7. On success: clears failure counters, updates `last_login_at`, calls `token_service.issue_tokens()`.
8. `TokenService.issue_tokens()` creates a JWT with RS256 signature (claims: sub, email, name, role, iat, exp, iss, aud, jti), generates a cryptographic refresh token, stores its SHA-256 hash in Redis under `auth:refresh:{hash}`, and tracks it in `auth:user_refresh:{user_id}` set.
9. Returns `AuthResult(user, TokenBundle)` to the route, which formats the standard response.

### Token Refresh with Reuse Detection

1. Client sends `POST /v1/auth/refresh` with `{refresh_token}`.
2. `token_service.rotate_refresh_token()` loads the token data from Redis (`auth:refresh:{hash}`).
3. If not found, checks `auth:refresh_used:{hash}`. If the used-token record exists (token theft detected), revokes the entire token family for that user via `revoke_all_refresh_tokens_for_user()`.
4. If valid: revokes old token, issues new access + refresh tokens, returns the new bundle.

### Google OAuth Flow

1. Frontend calls `GET /v1/auth/oauth/google/authorize?code_challenge=...&state=...`.
2. `OAuthService.build_google_authorize_url()` constructs the Google consent URL with PKCE S256 and all configured scopes.
3. User completes Google consent. Google redirects with `authorization_code`.
4. Frontend sends `POST /v1/auth/oauth/google/exchange` with `{code, code_verifier}`.
5. `OAuthService.exchange_google_code()` posts to Google's token endpoint, receives `{access_token, refresh_token, id_token}`.
6. Google `id_token` is verified via JWKS (`https://www.googleapis.com/oauth2/v3/certs`).
7. `AuthService.login_with_google()` finds or creates a User record, stores Google tokens encrypted in Vault, issues our own JWT.

## 5. Non-Technical Explanation

Think of Phase 2 as building the front door and key system for Alex's building. Before this phase, anyone could walk in — there was no door. Now, every visitor (API request) must show a valid key card (JWT token) to enter. The key card has the visitor's name and role printed on it, and it expires after one hour so a stolen card becomes useless quickly.

When you first arrive, you register at the front desk (registration endpoint) and receive your key card. You can also sign in using your Google account — the system verifies your identity with Google and then issues its own key card, so you don't need to remember a separate password.

If someone tries to break in by guessing your password, the door locks itself after five wrong attempts and stays locked for 30 minutes. Your key card can be refreshed without re-entering your password, and the old refresh slip is immediately shredded — if someone tries to use a shredded slip, the system assumes theft and locks all your doors.

All of Alex's future features — managing your calendar, sending emails, running AI conversations — require passing through this door first. Without Phase 2, none of those features can know who you are or whether you're allowed to use them.

## 6. Key Learnings

**RS256 over HS256.** We chose RS256 (asymmetric) so that any future microservice can verify tokens using the public key without needing the private signing secret. This is published at `/.well-known/jwks.json`. HS256 would have required sharing the secret key with every service that needs to validate tokens.

**Refresh token rotation with reuse detection.** Simply invalidating old refresh tokens isn't enough — if an attacker steals a refresh token and the legitimate client uses a rotated one, the attacker's next request with the stolen token must trigger a full revocation of the token family. Our implementation stores consumed tokens in `auth:refresh_used:{hash}` and revokes all tokens for that user if a consumed token is presented.

**Pydantic Settings and environment variables.** Pydantic's `BaseSettings` attempts to parse `list[str]` fields as JSON, which breaks when the `.env` file contains plain comma-separated values. We resolved this by storing list-type settings as raw strings and parsing them via `@property` methods (`parsed_cors_origins`, `parsed_google_oauth_scopes`).

**PKCE for OAuth.** We implemented the PKCE extension (`code_challenge` + `code_verifier` with S256) for the Google OAuth flow, which is required for public clients (mobile apps, SPAs) and recommended for all clients. This prevents authorization code interception attacks.

**Vault as a local stand-in.** The VaultService uses Fernet encryption (AES-128-CBC) with a key derived from `VAULT_ENCRYPTION_KEY` or `SECRET_KEY`. This mirrors the API surface of Supabase Vault so the switch to production Vault requires changing only the VaultService implementation, not any calling code.
