## 1. Phase Overview

### What This Phase Is
Phase 1 establishes the complete project foundation: a monorepo structure, a running FastAPI backend with all 12 database tables from `DATABASE.md`, Docker Compose orchestration for all services (API, Worker, Beat, Redis, PostgreSQL with pgvector), and a verified health check endpoint. No AI features, no voice — purely infrastructure.

### Why It Is Important
Every subsequent phase depends on this foundation. Phase 2 (Authentication) requires the `users` table and running API server. Phase 3 (AI Model Router) needs the database for session context storage. Phase 4+ needs the complete schema for tasks, reminders, calendar events, and conversations. Without a clean, verified foundation, every future phase would accumulate compounding errors.

## 4. Flow Explanation (Technical)

**Primary flow: Health Check (`GET /health`)**

1. Request arrives at FastAPI → `request_context_middleware` in `middleware.py` assigns a `request_id` and starts a timer
2. FastAPI routes to `health_check()` in `routes/health.py`
3. Handler calls `get_public_health()` in `services/health_service.py`
4. `get_public_health()` calls `ping_database()` in `core/database.py`
5. `ping_database()` acquires an async connection from the pool and executes `SELECT 1`
6. Result propagates back through the chain: `{"status": "healthy", "db": "connected"}`
7. Middleware adds `X-Request-ID`, `X-Response-Time`, and security headers to the response
8. `structlog` logs the request with method, path, status code, and duration

**Secondary flow: Docker Compose startup**

1. `docker compose up` starts `db` (PostgreSQL 16 + pgvector) and `redis` (7-alpine)
2. Health checks verify both services are ready (`pg_isready` and `redis-cli ping`)
3. `api` service starts: runs `alembic upgrade head` to apply the initial migration (creates all 12 tables, indexes, RLS policies, triggers)
4. `uvicorn` starts the FastAPI application on port 8000
5. `worker` and `beat` services start their Celery processes, connecting to Redis as broker

## 5. Non-Technical Explanation

Think of Phase 1 as building the foundation and framing of a house before adding any rooms, furniture, or appliances.

We've poured the concrete foundation (the database with all its tables), erected the structural frame (the API server), connected the water and electricity (Redis for caching and PostgreSQL for data storage), and installed the front door with a doorbell (the health check endpoint that confirms everything is working).

No one can live in this house yet — there's no furniture (no user features) and no smart home system (no AI). But without this foundation, adding those later would be impossible. Every wall, every room, every smart device in Phases 2–8 will be anchored to the structure built here.

The security system is also pre-wired: Row-Level Security ensures that when multiple users eventually share this house, each person can only access their own rooms.

## 6. Key Learnings

### Factory Pattern for FastAPI
The application uses `create_application()` instead of directly instantiating `FastAPI()`. This enables clean test isolation — test suites can create fresh app instances with test-specific settings without cross-contamination.

### Alembic with Async SQLAlchemy
Alembic migrations run synchronously, but the application uses async SQLAlchemy. The `config.py` provides `sqlalchemy_sync_database_url()` that swaps `+asyncpg` to `+psycopg` specifically for Alembic. This avoids maintaining two separate database URL configurations.

### Row-Level Security in the Initial Migration
RLS policies were included in the very first migration rather than being added later. This "security from day one" approach means there's never a window where data leaks are possible, even during development. The `auth.uid()` function gracefully defaults to the nil UUID when no JWT claim is present, preventing RLS from blocking local development.

### pgvector Extension Setup
The `vector` extension is enabled in the initial migration even though file embeddings aren't used until Phase 5. This ensures the database schema is fully consistent from the start and avoids migration ordering issues later.

### Fixed UUIDs in Seeds
Seed data uses deterministic UUIDs (`00000000-0000-4000-a000-000000000001`) rather than random ones. This makes seed data reproducible across dev environments and simplifies debugging — you always know the admin user's ID.
