## 1. Phase Overview

### What This Phase Is
This phase delivers the first fully end-to-end user-facing feature: Tasks and Reminders. Users can create, view, update, and complete tasks via REST API or natural language voice commands. Reminders fire as push notifications at exactly the right time via Celery Beat, with automatic retry logic and recurring schedule support.

### Why It Is Important
Tasks and reminders are the foundational productivity features that make Alex useful in daily life. They validate the entire pipeline built in Phases 1-3: authentication protects the data, the database stores it, the AI intent parser understands natural language commands, and the tool router executes them against real database records. Every later feature (briefings, email summaries, meeting action items) creates tasks as output.

**Purpose:** Hourly scan for past-due tasks.
**What it does:** Queries tasks where `due_date < now` and `status != done/cancelled`, publishes `task.overdue` events, and marks each flagged task in Redis to avoid duplicate notifications.

## 4. Flow Explanation (Technical)

1.  User says: "Remind me to call Arjun tomorrow at 3 PM"
2.  `POST /v1/command` receives the request → `IntentParser.parse()` runs.
3.  The heuristic parser detects "remind me to" pattern, extracts "call Arjun" as message, "tomorrow at 3 PM" as trigger time.
4.  Intent returns `{action: "create_reminder", params: {message: "call Arjun", trigger_at: "2026-03-28T15:00:00+05:30"}}`.
5.  `ToolRouter.execute_plan()` invokes `handle_create_reminder()` with the DB session.
6.  Since no explicit `task_id` is provided, `TasksService.create_task_with_reminder()` creates both a `Task` and linked `Reminder` in a single transaction.
7.  Every 30 seconds, `scan_due_reminders` checks if `remind_at <= now()`. When it triggers, it publishes a `reminder.triggered` event to Redis pub/sub and sets a 5-minute retry window.
8.  If no dismissal is recorded within 5 minutes, the retry logic fires a second delivery attempt.
9.  For recurring reminders, `next_recurrence_at()` calculates the next trigger (daily/weekly) and updates `remind_at` + resets status to `pending`.

## 5. Non-Technical Explanation

Think of Alex as a personal secretary who not only takes notes when you say things like "Remind me to call Arjun tomorrow at 3 PM" — but actually sets an alarm clock for that exact time. When the alarm goes off, Alex taps you on the shoulder (via push notification). If you don't respond within 5 minutes, Alex taps again. If you asked for a daily reminder, Alex automatically resets the alarm for the same time the next day without needing to be told again.

The "overdue" checker is like a supervisor who walks through the office every hour and sticks a red flag on any tasks that should have been done by now but haven't been.

## 6. Key Learnings

*   **Combined Task+Reminder Pattern:** Voice commands like "remind me to X" naturally create two records — a Task (the "what") and a Reminder (the "when"). Using `create_task_with_reminder()` in a single DB transaction ensures atomicity.
*   **Dateparser Configuration:** Setting `PREFER_DATES_FROM: "future"` and using the user's local time as `RELATIVE_BASE` prevents "Friday" from resolving to the previous Friday when it's already Saturday.
*   **Celery in Docker:** The worker and beat must share the same codebase image as the API container. The `celery_app.conf.update()` with `timezone="UTC"` and `enable_utc=True` prevents timezone drift between the scheduler and the database.
*   **Redis for Delivery State:** Using Redis (not PostgreSQL) for transient delivery state (retry tracking, overdue flags) keeps the database clean while providing fast atomic operations for the 30-second scan interval.
