## 1. Phase Overview

### What This Phase Is
This phase establishes the "brain" of the Antigravity application. It introduces the AI Model Router to abstract and handle LLM inference across local (Ollama) and cloud (Anthropic, OpenAI) providers. The core deliverable is the Intent Parser, which transforms natural language commands into structured JSON intent objects.

### Why It Is Important
Every subsequent voice or text feature in Antigravity depends on this intelligence layer to understand user commands and map them to concrete executable actions. Without reliable intent parsing and context-aware session memory, the application cannot delegate tasks accurately or hold a coherent conversation.

---

## 2. What Was Built

*   **`ai_router.py`**: The core AI abstraction layer implementing hot-switching between free (Ollama) and paid (Claude/OpenAI) modes.
*   **`intent_parser.py`**: The intent extraction engine that applies system prompts to categorize user commands, with a robust heuristic fallback mechanism.
*   **`tool_router.py`**: A registry-based middleware that executes the planned steps dispatched by the Intent Parser.
*   **`session_service.py`**: Redis-backed conversational short-term memory (5 turns, 30-minute TTL) for pronoun resolution.
*   **`command.py` (Schemas)**: Pydantic request/response models ensuring strict interface contracts for the intelligence layer.
*   **`command.py` (Routes)**: Five new API endpoints including the primary `/v1/command` flow and `/v1/chat` SSE streaming endpoint.
*   **`test_phase3_acceptance.py`**: A comprehensive end-to-end acceptance test suite covering both clear and ambiguous command resolution.

## 3. File-by-File Explanation

### `apps/api/app/services/ai_router.py`
**Purpose:** Single point of contact for all AI generation.
**What it does:** Reads user preferences to dynamically determine whether to route requests to Ollama or a paid cloud provider. It includes automated fallback chains (e.g., Anthropic -> OpenAI -> Free) and exposes both synchronous `generate()` and asynchronous `generate_stream()` interfaces.
**Key functions/classes:** `AIRouter` (Main service class), `AIResponse` (Unified response dataclass).
**Generated by:** Antigravity

### `apps/api/app/services/intent_parser.py`
**Purpose:** Interprets natural language into actionable machine instructions.
**What it does:** Uses the AI Router to pass user input and conversation context against highly tuned system prompts. It scores ambiguity and, if a command is unclear or if AI generation fails cleanly, triggers a fast, deterministic heuristic fallback parser.
**Key functions/classes:** `IntentParser` (Parsing engine), `_heuristic_parse` (Deterministic fallback logic).
**Generated by:** Antigravity / User Edit

### `apps/api/app/services/tool_router.py`
**Purpose:** Strategy pattern executor for parsed automation steps.
**What it does:** Processes the sequential `steps` array from the intent object, resolving dependencies using template variable substitution (e.g., `{{step_1_result}}`). It executes stub handlers that map to system actions.
**Key functions/classes:** `ToolRouter` (Execution engine), `@register_tool` (Handler registration decorator).
**Generated by:** Antigravity

### `apps/api/app/services/session_service.py`
**Purpose:** Manage conversational state.
**What it does:** Uses Redis to store recent user and assistant interactions. Limits context to 5 turns with an automatic 30-minute expiration window to optimize prompt payloads and maintain privacy.
**Key functions/classes:** `SessionService`, `get_context_string`.
**Generated by:** Antigravity

### `apps/api/app/api/routes/command.py`
**Purpose:** HTTP exposure of the intelligence layer.
**What it does:** Orchestrates the system's reaction loop: retrieving session context, parsing the intent, evaluating ambiguity, tracking analytics, and returning either a clarifying question or the results from the tool router.
**Key functions/classes:** `process_command` (Main POST route), `chat_stream` (SSE route).
**Generated by:** Antigravity

## 4. Flow Explanation (Technical)

1.  A `POST /v1/command` request arrives containing `{"input": "Remind me to call Arjun tomorrow..."}`.
2.  The route resolves the user's active AI mode via `PreferenceService` and fetches the conversation history from `SessionService`.
3.  The request is passed to `IntentParser.parse()`, which tries to contact the configured LLM through the `AIRouter`.
4.  If the Ollama instance is unreachable (e.g., binding issues with Docker Desktop), `IntentParser` detects the exact intent via its deterministic `_heuristic_parse` fallback.
5.  A JSON intent object is returned setting `action: "create_reminder"`.
6.  The `ToolRouter` receives the steps array, looks up the registered `@register_tool("create_reminder")` stub, and executes it.
7.  The final result, context, and a synthesized assistant response are wrapped in `CommandResponse` and returned to the client.

## 5. Non-Technical Explanation

Imagine you are talking to a highly capable secretary through an intercom. Before this phase, the intercom only worked if you pressed specific buttons in specific menus (like an archaic phone tree).

With Phase 3 complete, we've installed a "brain" behind the intercom. You can now use plain English. If you say "Remind me to do this later," the system's brain catches what you said, checks its short-term memory to figure out what "this" means, translates it into a checklist of concrete computer commands, and hands them off to the different departments. If it's confused, it knows exactly what clarifying question to bounce back to you.

## 6. Key Learnings

*   **Heuristic Fallback:** Relying purely on network-bound LLMs for control flow is risky. Implementing a deterministic regex-based fallback in the `IntentParser` guarantees the system fails gracefully and retains basic functionality (like setting reminders) even when the AI models go offline.
*   **Docker Host Resolution:** Accessing host-bound applications (like Ollama) from within a Docker container requires configuring `.env` correctly (`host.docker.internal`). Furthermore, Ollama must be configured to listen on all interfaces (`OLLAMA_HOST=0.0.0.0`) on the host machine to accept these bridged requests.
*   **Provider Agnosticism:** Abstracting the LLM SDKs behind the `AIRouter` interface proved highly effective. It allows the core logic to treat high-latency, unpredictable cloud models and fast local models exactly the same way.
