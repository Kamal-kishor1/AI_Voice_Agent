## Part 1 — Project Context

### What You Are Building

You are building **Alex**, a personal AI Operating System. Alex is a voice-first, text-capable intelligent assistant that connects to a user's Gmail, Google Calendar, Google Drive, and WhatsApp and allows them to manage their entire digital work life through natural conversation.

Alex can search files, send emails, send WhatsApp messages, book meetings, set reminders, transcribe meetings, generate morning briefings, and execute multi-step automations — all from a single voice or text command.

The system runs as a modular Python backend (FastAPI) with a Next.js web dashboard. The AI layer uses local open-source models (Ollama + Mistral 7B) in free mode and switches to Anthropic Claude or OpenAI in paid mode. All core features must work in free mode. Paid APIs are performance upgrades, not dependencies.

### Source of Truth Documents

Before starting any phase, read the following documents in this order:

1. `GOAL.md` — Final vision and capability list
2. `SYSTEM_DESIGN.md` — Architecture, components, data flows, API design
3. `TECH_STACK.md` — Every technology decision with rationale
4. `FEATURE_LIST.md` — All 70 features (F001–F070) with IDs, priorities, dependencies
5. `SECURITY.md` — Permission system, data handling rules, what Alex can/cannot do
6. `AI_INSTRUCTIONS.md` — System prompt, tool definitions, Alex's behavioural rules
7. `USER_FLOW.md` — All 10 user flows with step-by-step decision trees
8. `DATABASE.md` — Full schema, table definitions, relationships, indexes
8. `API_ENDPOINTS.md`
9. `ARCHITECTURE.md`
10. `AUTHENTICATION_REQUIREMENT_DOCUMENT.md`
11. `STRUCTURE.md`
12. `UI_UX.md`

### Non-Negotiable Rules for Every Phase

**Rule 1 — Free mode first.** Every feature must work with local/free tools before any paid API is integrated. Do not write code that requires Claude, OpenAI, or ElevenLabs as a hard dependency. Use the AI Model Router pattern so free and paid modes are interchangeable.

**Rule 2 — Follow the schema exactly.** The database schema in `DATABASE.md` is authoritative. Do not invent new tables or change column names without updating the schema document.

**Rule 3 — Respect the permission system.** Every action that sends an external communication (email, WhatsApp, calendar invite) must pass through the permission check defined in `SECURITY.md § 6.2`. No external send executes without user confirmation.

**Rule 4 — Document after every phase.** After completing each phase, create the corresponding `Documentation/phase_X.md` file using the exact template in Part 5 of this document. No phase is considered complete until its documentation file exists and is accurate.

**Rule 5 — Test before moving on.** Each phase defines an acceptance test. Do not start the next phase until the current phase's acceptance test passes cleanly.

## Part 2 — Active Toolchain

The development toolchain consists of four tools. Each has a specific, non-overlapping role. Using the wrong tool for a task wastes compute budget and produces lower-quality output — the tool assignment in each phase is a hard requirement, not a suggestion.

---

### Antigravity (Primary Coding Environment)

Antigravity is the primary environment where you work day-to-day. All code is written, run, iterated, and tested here. It is the connective tissue of the project — it takes outputs from Codex and Claude and wires them into a working system.

**Use Antigravity for:** day-to-day coding and file editing; reading and navigating the codebase; wiring together components generated by Codex; running acceptance tests and debugging failures; managing environment variables, Docker Compose, and local services; any task that requires iterative back-and-forth with the running code; small edits and fixes on existing files.

**Do not use Antigravity for:** generating large files from scratch (200+ lines) — use Codex for that; writing AI prompt templates — Claude handles those; architecture decisions — consult Claude before building.

---

### Codex — GPT-4.5 / GPT-5 Code at High or Extra High Compute

Codex running GPT-4.5 or GPT-5 (code-optimised) is the primary code generation engine. At High or Extra High compute settings, it reasons through complex logic, handles long file generation accurately, and writes production-quality Python and TypeScript from a well-scoped specification.

**Always set compute to High or Extra High.** Standard compute is insufficient for the complexity of Alex's codebase. The additional cost is justified — a Codex output at Standard compute that gets an integration wrong will cost far more time to fix than the compute savings. Extra High is preferred for any task involving algorithmic logic, multi-file generation, or integration with the AI Model Router.

**Use Codex for:** generating large, complete service files from scratch (e.g., the full `intent_parser.py`, `automation_engine.py`, `calendar_adapter.py`); complex algorithmic logic including the availability engine, topological sort in the Step Sequencer, fuzzy contact resolution, and the embedding pipeline; writing complete Celery task files with all job types, retry logic, and scheduling; generating the full SQLAlchemy ORM model layer from the `DATABASE.md` schema; writing complete API endpoint files from `API_ENDPOINTS.md` specifications; generating Docker and CI/CD configuration; any single task that would take more than 30 minutes to write manually.

**Do not use Codex for:** writing AI prompt templates (Claude produces significantly better prompts); architecture decisions or design trade-offs; code review or security analysis; writing the `phase_X.md` documentation files.

**Compute setting guide:**

| Task | Compute |

| Generating a complete feature module spanning multiple files | Extra High |
| Complex algorithms: topological sort, availability scoring, fuzzy match, embedding pipeline | Extra High |

### Phase 3 — AI Model Router & Core Intelligence

**Goal:** A working AI Model Router routing requests to Ollama (free) or Claude/OpenAI (paid) transparently. The Intent Parser correctly classifies user input and maps it to tool calls. This is the brain of the entire system — every subsequent phase depends on it.

**Tool assignments:**
- **Claude Opus 4.6** — Write and test all prompt templates first: the single-intent template (`AI_INSTRUCTIONS.md § 4.2`), the multi-intent template (`AI_INSTRUCTIONS.md § 4.3`), and the ambiguity detection template (`AI_INSTRUCTIONS.md § 4.4`). Test each against five representative inputs and verify the output JSON matches the intent object schema before any code is generated
- **Codex (Extra High)** — Generate the AI Model Router (`ai_router.py`), Intent Parser (`intent_parser.py`), Tool Router (`tool_router.py`), and SSE streaming endpoint. Pass the Claude-verified prompt strings as hardcoded constants in the Codex prompt
- **Antigravity** — Wire components together, run Ollama locally, test the complete free-mode path end-to-end
- **Gemini 2.5 Pro** — Before building, paste `SYSTEM_DESIGN.md § 4.2`, `AI_INSTRUCTIONS.md § 4.0`, and `FEATURE_LIST.md § F047–F050` simultaneously and ask Gemini to identify any gaps or contradictions between the three documents

**What to build:**

The AI Model Router must expose a single async interface — `generate(prompt, system, temperature, max_tokens, mode)` — that works identically regardless of which model is active. The active mode is read from the user's preferences table on every call, enabling hot-switching without a restart. Free mode connects to Ollama at `http://localhost:11434` using Mistral 7B (Q4_K_M) with LLaMA 3.1 8B as fallback. Paid mode uses Anthropic `claude-sonnet-4-20250514` with OpenAI `gpt-4o` as fallback.

The Intent Parser produces the structured intent object defined in `AI_INSTRUCTIONS.md § 4.1`. When `ambiguity_score > 0.4`, it returns the clarifying question and halts execution. Session context is stored in Redis (`session:{id}:context`, 30-minute TTL) and injected into every call.

Streaming responses use Server-Sent Events from the chat endpoint.

**Features covered:** F047, F048, F049, F050, F054

**Acceptance test:** "Remind me to call Arjun tomorrow at 3 PM" produces an intent object with `action: "create_reminder"`, `confidence > 0.9`, and a correct `trigger_at` timestamp. "Send it to him" with no prior context produces `ambiguity_score > 0.4` and a clarifying question. Both the Ollama and Claude API paths return valid intent objects.

### Phase 5 — File Search System

**Goal:** Every file in the user's Google Drive is indexed and searchable by semantic meaning. The user can find any file by describing its contents in plain English.

**Tool assignments:**
- **Codex (Extra High)** — Generate the complete file indexing pipeline (`file_indexer.py`) and search service (`file_search_service.py`). This is one of the most algorithmically complex phases — Extra High is mandatory
- **Gemini 2.5 Pro** — Before building, paste `DATABASE.md § 4.9–4.10`, `FEATURE_LIST.md § F009–F013`, and `SYSTEM_DESIGN.md § 4.4` simultaneously to check for any inconsistencies in embedding dimensions, indexing schedule, and search scoring logic
- **Claude Opus 4.6** — Review the scoring and auto-select logic against `FEATURE_LIST.md § F011` thresholds (0.75 score, 0.15 gap); review disambiguation flow against `USER_FLOW.md § 3.3.1`
- **Antigravity** — Run the indexer against a real Drive, verify embeddings are stored correctly in pgvector, test search with various queries

**What to build:**

Implement the Drive indexing pipeline: authenticate via stored OAuth token, fetch file metadata, extract text from PDF (`pdfplumber`), DOCX (`python-docx`), XLSX (`openpyxl`), and Google Docs (export API), chunk at 512 tokens with 50-token overlap, generate 384-dimensional embeddings via `all-MiniLM-L6-v2`, store in the `files` table and pgvector. Schedule `fileIndexJob` every 15 minutes as a delta sync.

Implement `POST /v1/files/search`: embed the query, cosine similarity search via pgvector `<=>` operator, apply +0.05 recency boost for files modified in the last 30 days, auto-select if top score > 0.75 and gap to second result > 0.15, otherwise return the ranked list. Register the `search_files` tool with the AI Model Router.

**Features covered:** F009, F010, F011, F012, F013

**Acceptance test:** Searching "quarterly sales report" on a Drive with 20+ files returns the correct file even if it is named `Q3_Data_Final.xlsx`. Multiple near-match results present a disambiguation list. Search latency for a 2,000-file index is under two seconds.

## Part 4 — Reviewing Codex Output

## Part 7 — Decisions Already Made

The following decisions are locked. Do not re-evaluate them during any build phase.

**Architecture:** Modular monolith. Python 3.11 + FastAPI backend. Next.js 14 frontend. No microservices in v1.0.

**Database:** PostgreSQL 16 via Supabase with pgvector. Replaces any prior mention of SQLite or ChromaDB. See `TECH_STACK.md — Architecture Reconciliation Note`.

**AI Model approach:** Hybrid — free/local first, paid as optional upgrade. The AI Model Router (F048) is the single abstraction layer. No module calls Claude or Ollama directly.

**Free mode stack:** Ollama + Mistral 7B (LLM), faster-whisper (STT), Coqui TTS (TTS), Porcupine (wake word), all-MiniLM-L6-v2 (embeddings), Whoosh (keyword search).

**Paid mode stack:** Anthropic `claude-sonnet-4-20250514` (LLM), OpenAI Whisper API (STT), ElevenLabs (TTS), OpenAI `text-embedding-3-small` (embeddings).

**Communication integrations:** Gmail API (email), Meta WhatsApp Business Cloud API v21.0 (WhatsApp), Google Calendar API v3 (calendar). Twilio Sandbox is acceptable for development only.

**Infrastructure:** Railway (backend + worker + Redis), Vercel (frontend), Supabase (DB + storage + auth), GitHub Actions (CI/CD).

**Permission model:** The L0–L3 system from `SECURITY.md § 6.1` applies to all actions. It cannot be bypassed by any generated code.

**Documentation:** Claude Opus 4.6 writes all `phase_X.md` files. Mandatory after every phase. No exceptions.

**Backend:** FastAPI. Confirmed per `TECH_STACK.md v1.0`. Not open for re-evaluation.
